# Parallel Word Counting in a Text Corpus with MPI

This repository implements the lab **"Parallel Word Counting in a Text Corpus
with MPI"** for the Parallel Computing course at Universidad del Norte.
It provides a sequential baseline, a first MPI implementation using
**static round-robin distribution with collective communication**, and a
second MPI implementation that **reduces load imbalance via a dynamic
master-worker scheme using point-to-point communication**.

**Normative references used to plan and evaluate this experiment:**

* Lab statement: *Parallel Word Counting in a Text Corpus with MPI*
  (`Parallel Word Counting in a Text Corpus with MPI.pdf`, version of the
  spring 2026 session).
* Theory deck: *MPI — Message Passing Interface* (Augusto Salazar Silva,
  Universidad del Norte). The "Retos del paralelismo" section
  (planificación, sincronización, carga por comunicación, balanceo de
  cargas) shapes the design of `mpi2.py`.
* Rubric SO (6): *"an ability to develop and conduct appropriate
  experimentation, analyze and interpret data, and use engineering
  judgment to draw conclusions."*

## 2. Problem Description

Given:

* A query file `consulta.txt` with one target word per line.
* A corpus of multiple text files `file_XXXX.txt` (generated by
  `generator.py`).

Required outputs:

1. The count of how many times each word from `consulta.txt` appears in the
   corpus.
2. The aggregation of those partial counts.
3. The **top 10** most frequent query words.

The dataset for this lab has **3000 files**, **44 951 458 tokens** and
produces **3 631 778 occurrences** of the query words. All three
implementations (`baseline_secuencial`, `mpi1`, `mpi2`) produce the same
top 10, which is the correctness check defined by Part 0 of the lab.

## 4. Experimental Plan

### 4.a Sequential Baseline — what it does and how

`baseline_secuencial.py` (provided, unchanged) reads `consulta.txt`,
iterates over every `file_*.txt` in `dataset/`, counts how many times each
query word appears, and prints the top 10. It runs in a single Python
process with no parallelism. It is used as:

* the **correctness baseline** (top-10 must match in every parallel run),
* the **timing baseline** `T_seq` for computing speedup and efficiency.

### 4.b MPI Version 1 — what it does and how

`mpi1.py` implements the 7 steps required by Part 1 of the lab:

1. Rank 0 reads `consulta.txt`.
2. Rank 0 **broadcasts** the query set to all ranks (`comm.bcast`).
3. Rank 0 collects the list of corpus files with `glob`.
4. The file list is split **statically** by a round-robin slice
   `files[i::size]` and **scattered** to all ranks (`comm.scatter`).
5. Each rank counts local occurrences in its assigned files.
6. Partial counters are **gathered** in rank 0 (`comm.gather`).
7. Rank 0 builds the global counter and prints the top 10.

`mpi1.py` reports the number of files assigned to each rank and the
local processing time of each rank, as required by Part 1. It also prints
the total wall-clock time (`MPI.Wtime`) as `EXECUTION_TIME=...` so that
`run_all.sh` captures it in `times_summary.csv`. It uses only
**collective communication** (`bcast`, `scatter`, `gather`, `Barrier`),
which is precisely the set of primitives Part 1 prescribes.

### 4.c Test procedure

For each implementation (`baseline_secuencial`, `mpi1`, `mpi2`) and for
each process count `p ∈ {1, 2, 4, 8}`, the procedure defined by Part 2 of
the lab is applied:

1. Run the configuration **3 times** through `run_all.sh` to dampen
   one-off OS noise.
2. Record the total execution time (`EXECUTION_TIME=` line, captured by
   the shell script in `times_summary.csv`).
3. Record the local execution time of every rank (printed by the program
   into the corresponding `results/logs/*_npP_runR.log` file).
4. Compute the **average** total time `T_p` across the 3 runs of each
   configuration.
5. Compute **speedup** `S_p = T_seq / T_p`.
6. Compute **efficiency** `E_p = S_p / p`.
7. Quantify **load imbalance** per run as
   `imbalance = (t_max − t_min) / t_max` over the local rank times.

The number of cores available inside the container is queried with
`docker run --rm augustosalazar/slim-mpi:2 nproc` and is reported in
-3.6.

### 5.d MPI Version 2 — implementation correcting the imbalance, with timing results

**Implementation (Part 3 of the lab).** `mpi2.py` implements a
**dynamic master-worker scheme using point-to-point communication**.
The design follows the *Retos del paralelismo → Balanceo de cargas*
section of the MPI theory deck: detect and correct imbalances at runtime,
so that no rank stays idle while another is still working.

Workflow:

1. Rank 0 (master) broadcasts the query set (`comm.bcast`).
2. Rank 0 keeps the queue of all corpus files and **participates as a
   worker** instead of being a pure coordinator. This avoids wasting one
   process.
3. Workers (rank > 0) send `TAG_REQUEST` to rank 0 asking for work.
4. The master replies with a **chunk of `CHUNK_SIZE = 25` files**
   (`TAG_WORK`) or with `TAG_STOP` once the queue is empty.
5. Between request rounds the master pulls a chunk for itself and
   processes it, polling for pending requests with `Iprobe`.
6. Workers loop request → process → request until they receive `TAG_STOP`.
7. Each worker finally sends its partial counter, token count, files
   processed and local elapsed time to rank 0 (`TAG_RESULT`).
8. Rank 0 merges everything and prints the top 10, the per-rank
   breakdown, the load-balance metrics and `EXECUTION_TIME=`.

Design choices and what they buy:

* **Chunks of 25 files per message** reduce communication overhead from
  3000 messages (file-per-message) to ≈120. This addresses the *Carga por
  la comunicación* challenge from the theory deck.
* **Rank 0 also processes**, so no process is wasted on pure coordination.
* **Self-correcting imbalance**: the rank that finishes first asks for
  more, automatically pulling extra work.

`results/times_summary.csv`):

## 6. Analysis

### 6.a Did the first MPI implementation improve execution time compared to the sequential baseline?

**Question:** does `mpi1` beat `baseline_secuencial`?

**Answer: yes, in every configuration.** Using the numbers in -5.a–-5.b:

* `p = 2`: 19.429 s → 8.004 s → **2.43× faster**.
* `p = 4`: 19.429 s → 4.562 s → **4.26× faster**.
* `p = 8`: 19.429 s → 2.982 s → **6.52× faster**.

Each ratio is computed from the average of 3 runs, with a CoV ≤ 3.5 %
between runs (-5.b), so the improvement is reproducible and not a
measurement artifact.

### 6.b Was the observed speedup linear?

**Question:** is `S_p ≈ p`?

**Answer: no.** At `p ∈ {2, 4}` it is *super-linear*; at `p = 8` it is
*sub-linear*.

| `p` | Ideal S_p | Measured S_p | Efficiency E_p |
| --- | --- | --- | --- |
| 2 | 2.0 | 2.43 | **1.21** |
| 4 | 4.0 | 4.26 | **1.06** |
| 8 | 8.0 | 6.52 | **0.81** |

* **Super-linear at p = 2, p = 4 (E > 1)** is plausibly explained by two
  effects, both legitimate and reproducible:
  1. **I/O parallelism.** Reading 3000 small text files is partly disk-bound.
     With multiple processes issuing reads concurrently, the kernel
     interleaves I/O wait with CPU work — something a single-process
     baseline cannot do.
  2. **Cache locality.** Each rank works over a smaller per-process file
     set (1500 files at p = 2, 750 at p = 4), so the working set fits more
     comfortably in CPU caches and Python's internal dict lookups perform
     better.
* **Sub-linear at p = 8 (E = 0.81)** cannot be blamed on oversubscription:
  the container reports `nproc = 16`, well above `p = 8`. The dominant
  causes here are:
  1. **Load imbalance ≈14 %** (-5.c) — the slowest rank holds back the
     gather.
  2. **Filesystem I/O contention** — with more concurrent readers, the
     bind-mounted volume becomes a contention point.
  3. **Collective communication overhead** grows with `p`.

### 6.c Is there evidence of load imbalance? How was it observed?

**Question:** is imbalance present in v1, and how was it detected?

**Answer: yes, and it was detected by inspecting the per-rank local times
printed by `mpi1.py`.** See -5.c for the full table. Summary:

* `p = 2`: imbalance 0.15 % – 1.19 %. Negligible — the regenerated dataset
  is very uniform.
* `p = 4`: imbalance 3.83 % – 5.73 %. Mild.
* `p = 8`: imbalance **12.97 % – 14.40 %**. Significant. In every one of
  the 3 runs, rank 2 was the slowest by ~0.4 s, suggesting either a
  systematically heavier slice `files[2::8]` or stable OS-level contention
  on that rank.

Because the lab's metric is computed as `(t_max − t_min)/t_max`, this
observation also gives an upper bound on the wall-clock time we could
have saved with a perfect balancer: ≈14 % at `p = 8`, ≈5 % at `p = 4`,
≈1 % at `p = 2`.

### 6.d Did the second implementation reduce load imbalance?

**Question:** does v2 reduce the imbalance evidenced in -5.c / 6.c?

**Answer: yes, by roughly one order of magnitude in every configuration.**

| `p` | Imbalance v1 (worst run) | Imbalance v2 (worst run) | Reduction |
| --- | --- | --- | --- |
| 2 |  1.19 % | 0.10 % | **≈12×** |
| 4 |  5.73 % | 2.06 % | **≈3×**  |
| 8 | 14.40 % | 3.54 % | **≈4×**  |

The dynamic master-worker scheme keeps every rank busy until the global
queue is empty, so the only residual gap is the last chunk each rank
processes (≈125 ms on a ≈5–11 s workload, i.e., bounded to a few
percent — which is what we observe).

### 6.e Did the improved distribution strategy produce a real performance improvement?

**Question:** does v2 also run faster than v1?

**Answer: no — not on this dataset.** Despite the imbalance reduction, v2
is 40–63 % slower than v1 in every configuration (-5.d). The engineering
reasoning, grounded in the measurements:

1. **The corpus is already nearly balanced.** v1's worst imbalance is
   only ≈14 % (at `p = 8`); at `p = 2` it is ≈1 %. There is little wasted
   wall-clock time for v2 to recover.
2. **Communication overhead added by v2 is real.** Each chunk costs one
   point-to-point round-trip between worker and master. The master cannot
   answer a request while processing its own chunk, so each worker pays a
   latency penalty at every chunk boundary. The theory deck (*Carga por la
   comunicación*) anticipates exactly this trade-off.
3. **Master concentration.** The master pulls a new chunk for itself as
   soon as it serves the queue, so it out-paces the workers and ends up
   doing most of the work (`p = 2`: master 2175 files vs worker 825 — see
   `results/logs/mpi2_np2_run1.log`). This balances the per-rank elapsed
   times almost perfectly but does not shrink the total time, because all
   that extra processing serializes on rank 0.

**Engineering conclusion:** load balancing has a non-zero cost; it
amortizes only when the imbalance it removes is larger than the
communication overhead it introduces. For a corpus this homogeneous,
v1's simpler design wins.

### 6.f What limitations affected the experiment?

* **Single host, no real cluster.** All ranks run inside one Docker
  container with shared-memory MPI transport. Network latency, NUMA
  effects and inter-node bandwidth are absent from the measurements.
* **`nproc = 16` masks oversubscription effects.** Our largest `p = 8` is
  well below 16, so we never exercise the oversubscription regime — that
  protects us from one kind of overhead but also means we cannot study
  how the two schemes behave when ranks must time-share cores.
* **Dataset homogeneity.** The corpus generated by the provided
  `generator.py` has fairly uniform file sizes. This is the single
  biggest factor explaining why v2 does not pay off in wall-clock time;
  a heavy-tailed corpus would likely invert the v1-vs-v2 comparison.
* **OS noise** in a containerized environment cannot be eliminated, only
  averaged. We mitigated it with 3 runs per configuration and report
  CoV ≤ 3.5 % to certify the residual noise is small.
* **Granularity choice.** `CHUNK_SIZE = 25` in v2 was picked empirically;
  we did not run a chunk-size sweep, which is the natural follow-up
  experiment.
* **I/O part of the measured time.** Reading 3000 files from a
  bind-mounted volume is itself partly serialized by the underlying
  filesystem, contributing to the saturation observed at `p = 8`.

## 7. Conclusions

The parallel implementations **improved execution time** with respect to
the sequential baseline at every `p` tested:

* `mpi1` (static round-robin): 2.43× / 4.26× / 6.52× faster at `p = 2 / 4 / 8`.
* `mpi2` (dynamic master-worker): 1.74× / 2.62× / 4.10× faster at the
  same `p`.

**The most important problem observed in the first parallel version is
load imbalance at `p = 8`** (≈14 %), where rank 2 was systematically the
slowest. At lower `p` the imbalance was negligible (<6 %), because the
regenerated dataset has fairly uniform file sizes — a factor we did not
control and that affects how much room for improvement v2 has.

**The second version achieved its design objective** stated by Part 3 of
the lab: it reduced the load imbalance by roughly one order of magnitude
in every configuration (14.4 % → 3.5 % at `p = 8`; 1.2 % → 0.1 % at
`p = 2`), using a dynamic master-worker scheme with point-to-point
communication exactly as the MPI theory deck prescribes for the
*balanceo de cargas* challenge. **However, on this corpus that imbalance
reduction did not translate into a faster wall-clock time** — v2 was
40–63 % slower than v1 because the corpus was homogeneous enough that
the communication overhead introduced by the dynamic scheme exceeded the
imbalance overhead it removed.

**Final judgment, grounded in the evidence:**

* Parallelization vs. sequential — **clear win** for both versions.
* v1 vs. v2 on this dataset — **v1 wins on time, v2 wins on imbalance.**
* The lab's Part 3 objective ("reduce the load imbalance observed in
  Part 1") was **met** (-5.d, -6.d). The natural follow-up — *show that
  the imbalance reduction also reduces wall-clock time* — was **not met
  on this dataset**, and -6.e / -6.f explain why under conditions a
  practitioner can identify in advance: when imbalance is already
  small (≪10 %), simpler static distribution outperforms dynamic
  load balancing.

This is the kind of trade-off the engineering judgment criterion of
rubric SO-6 asks the team to surface explicitly, with measurements
supporting both directions of the argument.
